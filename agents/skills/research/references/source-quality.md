# Source quality

A grounded answer is only as good as the source under it. Judge the source before you trust the fact.

## Rank by authority

Not all sources are equal. From most to least trustworthy for a technical fact:

1. The project's own docs, repo, and release notes. This is where the API and the version actually live.
2. Official standards, RFCs, and vendor documentation for a service.
3. Well kept third-party references that track the primary source closely.
4. Blog posts, tutorials, and forum answers. Useful for approach and context, weak for exact facts.
5. Anything undated or anonymous. Treat it as a lead to confirm elsewhere, not as an answer.

When a blog and the official docs disagree, the docs win. When a tutorial shows an API that the docs don't mention, trust the docs and suspect the tutorial is old.

## Check recency

A correct fact from an old page is still wrong if the thing changed. For anything version-sensitive:

- Find the publish or update date of the page. An undated page is a warning.
- Prefer the version's own changelog or release notes over a summary written for an earlier version.
- Watch for tutorials that pin an old major version. The API shape may have moved.
- When you cite a version number, cite where and when you read it, so a later reader can tell if it's gone stale.

## Spot stale or invented facts

The two ways research goes wrong: a source is out of date, or you filled a gap from memory and called it research.

- If a fact came from your own recall rather than a source you opened, mark it as unverified until you confirm it.
- Be suspicious of an API signature, flag, or config key that no primary source shows. If you can't find it in the docs or the repo, assume it doesn't exist in the form you remember.
- Read the actual passage for load-bearing claims. A synthesized summary can smooth over a detail that changes the decision.

## Resolve disagreement

When good sources conflict:

1. Check dates first. The disagreement is often just old versus new.
2. Prefer the more authoritative source when both are current.
3. If they still conflict, say so in your summary, give both, and pick one with the reason. Don't hide the conflict behind a confident single answer.

## Record the trail

For each load-bearing fact, keep the source link and the date you read it. A grounded summary lets the next step and the user check your work instead of taking it on faith. If a fact matters and you couldn't confirm it, say that plainly rather than presenting a guess as settled.
